# Issue の実装

Issue 1件を、ブランチを切るところから PR を出すところまで進める。このスキルを呼ばれたこと自体を、ブランチの作成・コミット・push・PR の作成の依頼として扱う。

## なぜこの手順にするか

- **テストを別のエージェントに、実装より先に書かせる**：実装したのと同じセッションでテストを書くと、実装を知っているために「このコードが通るケース」を書いてしまい、実装の見落としをテストも一緒に見落とす。
- **test-writer は別の worktree で動かす**：同じ作業ツリーだと、書きかけの実装を読んでしまうおそれがある。指示に頼らず、見えないようにする。
- **渡すのは Issue の番号だけ**：プロンプトに実装の案などを書くと、そこから実装の文脈が漏れる。Issue と決めごとは test-writer が自分で読む。

## 自動実行のとき

最初に `printenv LOCAL_TODO_AUTO` を実行する。`1` が出れば自動実行（`make auto` から呼ばれた）、それ以外（何も出ない）は対話（ユーザーが呼んだ）とする。プロンプトの言葉では見分けない。たまたまその言葉を含む依頼で取り違えないため。`echo "${LOCAL_TODO_AUTO:-}"` のように変数を展開する書き方は、許可の一覧にあっても確認が出るので使わない。

対話のときは、各手順に書いたとおりにユーザーに聞いて止まる。自動実行のときは、ユーザーに聞く場面でも聞かずに、次のどちらかで止まる。その場にいる人には、権限の確認（組織の設定で `make` や `git push` に要る）に答えることだけを任せ、設計の判断は grill-issues で前もって済ませておくため。どちらで止まるかは、各手順の「自動実行のとき」に書く。

- **needs-human**：Issue の中身の問題で止まる。ブランチを切ったあとなら、先に「途中までの変更を残す」を行う。そのあと、Issue に下の形でコメントし（`gh issue comment <番号> --body-file <ファイル>`）、`gh issue edit <番号> --add-label needs-human` で `needs-human` を付けて終わる。
- **中断**：手元の状態の問題で止まる。Issue には何もせずに終わる。`make auto` はそこで止まる。

コメントの形。1行目は決まった書き方にして、手で書いたコメントと見分ける。

```
自動実行で止まりました（implement-issue / 手順 <番号>）

## 止まった理由

## 決めてほしいこと

## 途中までの変更
（あれば。push したブランチの名前や、残した test-writer の worktree のパスとブランチ）
```

**途中までの変更を残す**：

- コミット前の変更があれば、手順 8 と同じく、この Issue で変えたファイルだけを `git add` してコミットする。`git add -A` や `git add .` は使わない。ほかの変更が混ざらないようにするため。test-writer の worktree はリポジトリの中（`.claude/worktrees/…`）に作られる。.gitignore に入れてあるが、まとめて追加すると、入れ忘れたときなどに埋め込みリポジトリとしてコミットされてしまう。
- メッセージの1行目は「途中まで：<何をしたか>」にする。`git push -u origin <ブランチ>` で push し、PR は出さずに `git switch main` で main に戻る。
- test-writer の worktree が残っているあいだ（手順 2 で呼んでから、手順 5 で片づけるまで）に止まったときは、どの手順で止まっても worktree は片づけずに残す。コメントの「途中までの変更」に、worktree のパスとブランチを書く。取り込んでいないテストを、あとで人が見つけられるようにするため。

- `in-progress` ラベルにはさわらない（`make auto` が扱う）。
- 終わる前に、結果を `LOCAL_TODO_RESULT` のファイルに書く（「最後の報告」）。`status` は `完了`（PR を出した）・`needs-human`・`中断` のどれか。

## 1. ブランチを切る

- Issue を読む：`gh issue view <番号> --json title,body --jq '"\(.title)\n\n\(.body)"'`
- 「先に終わっている必要がある Issue」が閉じているかを確かめる。閉じていなければ、進めてよいかユーザーに聞く。
  - 自動実行のとき：needs-human で止まる。
- コミット前の変更が残っていないことを確かめる（`git status --short`）。残っていれば、どうするかユーザーに聞く。
  - 自動実行のとき：中断する。
- その Issue のブランチ（`feature/<番号>-*`）が、手元（`git branch --list 'feature/<番号>-*'`）にも origin（`git ls-remote --heads origin 'refs/heads/feature/<番号>-*'`）にもないことを確かめる。あれば、前に途中で止まった実装が残っているので、どうするかユーザーに聞く。そのブランチから続けると、test-writer の worktree が途中までの実装を含むコミットから切られてしまう。
  - 自動実行のとき：中断する。
- main を最新にして、ブランチを切る：`git switch main`、`git pull --ff-only`、`git switch -c feature/<番号>-<短い英語の名前>`

## 2. test-writer を呼ぶ

Issue の「やること」に `LocalTodoTests/` のテストファイルが挙がっているときだけ呼ぶ。

- Agent ツールで、`subagent_type: "test-writer"`、`isolation: "worktree"` を指定して呼ぶ。
- プロンプトは「Issue #<番号> のテストを書いてください。」だけにする。実装の案、型の中身、注意点などを付け足さない。
- フォーク（`subagent_type: "fork"`）は使わない。会話を引き継ぐので、別のセッションにする意味がなくなる。
- worktree は、呼んだ時点のコミットから切られる。実装は、test-writer を呼んだあとまでコミットしない。

テストファイルが挙がっていなければ呼ばない。PR の本文に「テストの対象なし」と書く。実装の途中で、テストを書くべきロジックが出てきたら、止まってユーザーに聞く。

- 自動実行のとき：テストを書くべきロジックが出てきたら、needs-human で止まる。

## 3. 並行して実装する

- test-writer がテストを書いている間に、Issue の「やること」に沿って実装を進める。まだコミットしない。
- test-writer の結果を待たずに、実装を見てテストを自分で書かない。テストは test-writer の分だけにする。

## 4. test-writer の報告を読む

報告には、ケースの一覧、推測で決めた名前、Issue の曖昧なところが書かれている。

- 曖昧なところが挙がっていれば、ユーザーに確かめる。決まった内容が Issue と違えば、Issue の本文も直してよいかユーザーに聞く。
  - 自動実行のとき：曖昧なところが、テストのケースや期待値にかかわるときだけ、needs-human で止まる。名前の推測など、それ以外の曖昧なところは、そのまま進めて、8 で PR の本文に書く。
- 推測で決めた名前は、5・6 で実装と合わせるときの手がかりにする。

## 5. テストを取り込む

Agent ツールの結果に、test-writer の worktree のパスとブランチが出る。test-writer はコミットしないので、テストは worktree の中にコミット前の変更として残っている。ブランチからは取り込めない（`git checkout <ブランチ> -- <パス>` では何も取れない）。

次の順に進める。片づけは必ず最後にする。先に消すと、何が変わっていたかを確かめられなくなる。

1. **確かめる**：`git -C <worktree のパス> status --porcelain --untracked-files=all` で、変わったファイルを見る。`LocalTodoTests/` 以外のファイルが変わっていたら、取り込まずにユーザーに知らせて止まる（test-writer の決まりに反しているため）。worktree は片づけずに残しておく。
   - 自動実行のとき：needs-human で止まる。
2. **取り込む**：`LocalTodoTests/` の中の、追加・変更されたファイルを、worktree のパスからこちらの同じ場所にコピーする：`cp <worktree のパス>/LocalTodoTests/<ファイル> LocalTodoTests/`。worktree は、こちらのブランチを切ったときと同じコミットから切られているので、既存のテストファイルもファイルごとコピーしてよい。
3. **取り込めたことを確かめる**：1 で見たファイルごとに `diff <worktree のパス>/LocalTodoTests/<ファイル> LocalTodoTests/<ファイル>` を実行し、何も出ないことを確かめる。`git status --short LocalTodoTests/` にも、そのファイルがすべて出ていることを確かめる。
4. **片づける**：worktree にはコミット前の変更が残っているので、`git worktree remove` は `--force` を付けないと失敗する。`git worktree remove --force <worktree のパス>` で消し、`git branch -D <worktree のブランチ>` を実行する。

## 6. テストと実装を合わせる

- ビルドを通すための直しだけはしてよい：型・メソッド・引数・エラーの型の名前、テストのヘルパーの呼び方など。
- 何を確かめるか（ケースと期待値）は変えない。ケースを消す、期待値を変える、境目をずらす必要があると思ったら、止まってユーザーに聞く。テストが Issue と食い違っているのか、実装が間違っているのかは、ユーザーが決める。
  - 自動実行のとき：needs-human で止まる。
- テストに合わせて実装を直すのはかまわない。
- テストを直したら、何をどう直したかを控えておく（8 で PR の本文に書く）。

## 7. make check

```bash
make check
```

フォーマット・リント・テストがすべて通るまで直す。画面にかかわる変更なら、アプリを起動して動きも確かめる。

- 自動実行のとき：
  - 3回直しても通らなければ、needs-human で止まる。直し続けて止まらなくなるのを防ぐため。
  - 画面にかかわる変更でも、アプリは起動しない。見て確かめる人がいないため。8 で PR の本文に「画面の確認はしていない」と書き、マージするときに人が確かめる。

## 8. PR を出す

- 変えたファイルだけを `git add` してコミットする。メッセージは日本語で、1行目に何をしたか、本文になぜそうしたかを書き、`Closes #<番号>` を入れる。末尾の署名は、セッションの指示に従う。
- `git push -u origin <ブランチ>` のあと、`gh pr create` で PR を出す。本文には次を書く。
  - `Closes #<番号>`（1行目）。GitHub は、PR がどの Issue を閉じるか（`closingIssuesReferences`）を PR の本文から読む。コミットメッセージに書くだけでは読まれず、`make review` も `make auto` もこれで Issue を見つけるため
  - やったこと
  - テストを書いたのは test-writer であること。テストの対象がなければ「テストの対象なし」
  - テストの名前を直したときは、何をどう直したか（code-reviewer が、ケースや期待値を変えていないか確かめられるように）
  - Issue の決めごとから外れた点
  - 自動実行のとき：進めた曖昧なところ（4）。画面にかかわる変更なら「画面の確認はしていない」（7）
- PR を出したら、`make review PR=<PR の URL>` の実行をユーザーに案内する（CLAUDE.md の「コードレビュー」）。自分では実行しない。
  - 自動実行のとき：案内しない。`make review` は `make auto` が呼ぶ。

## 最後の報告

自動実行のときは、終わる前に、結果を `make auto` に渡す。

1. `printenv LOCAL_TODO_RESULT` でファイルのパスを読む。
2. そのパスに、Write ツールで次の形の JSON を書く。`status` は `完了`・`needs-human`・`中断` のどれか。`pr_url` は PR の URL（なければ空の文字列）。`summary` は、止まった理由か、したことの短いまとめ。

   ```json
   {"status": "完了", "pr_url": "https://github.com/…/pull/<番号>", "summary": "…"}
   ```

3. 最後に「終わりました。/exit で閉じてください。」と伝える。閉じると `make auto` が次へ進む。


ユーザーには次を伝える。

- 何を実装したか
- test-writer が書いたテストの件数と、自分で足したケースの主なもの
- テストの名前を直したか、直したなら何を
- make check の結果（テストの件数）
- PR の URL と、`make review` の案内
