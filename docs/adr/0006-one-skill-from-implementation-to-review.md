# 全自動化はやめ、実装からレビュー対応までを1つのスキルで対話しながら進める

ADR-0005 の `make auto` はやめる。組織の設定による Claude Code の制限が厳しく、実際に動かしても、理想とする挙動には届かなかった。代わりに、人が Issue を指定して implement-issue を呼び、ブランチを切るところからレビューコメントへの対応までを、その1回の依頼で対話しながら進める。マージは人がする。設計の判断を前もって済ませる必要がなくなったので、スキルは迷ったらその場でユーザーに聞く。`ready` などのラベルも、読むものがなくなるので使わない。

- **`make review` は、コードを書いたセッションが呼ぶ**：レビュアーは `claude -p` の別のプロセスで動くので、ADR-0003 の「書いたのとは別のセッションでレビューする」はそのまま守れる。ADR-0005 では、書いた側が気に入らないレビューをやり直せてしまうという理由でこの形を退けた。今回は、PR 全体のレビューを1つの PR につき1回だけにする決まりで、その心配を抑える。1人で作るアプリなので、決まりで縛れば足りると判断した。
- **直したあとの確かめは、コメントごとの `make re-review` だけにする**：PR 全体をもう一度レビューすると、新しい指摘が出て終わらなくなるおそれがある。上の「1回だけ」の決まりともぶつかる。
- **Issue を詰めたときのドキュメントは、その Issue の実装 PR に入れる**：grill-with-docs で書いた ADR・CONTEXT.md・TODO.md の変更は、コミットせずに残しておく。implement-issue がブランチを切ったら、test-writer を呼ぶ前に、まずその変更をコミットする。test-writer の worktree はコミット済みの状態から切られるので、コミットしないと、決めたことが test-writer から見えない。ドキュメントだけの PR は出さない。マージを待つ手間がかかるうえ、`ready` というラベルで「決めたことが main に入った」と示す必要もなくなったため。

## Considered Options

- PR を出したところでスキルを止め、人が `make review` を打ってから続ける：レビューの独立性はいちばん強い。ただ、一連のフローが2回の依頼に分かれる。
- Agent ツールのサブエージェントで code-reviewer を呼ぶ：プロンプトを書くのがコードを書いたセッションなので、書いた側の文脈が入る（ADR-0005 と同じ理由）。
- 対応が終わったあと、PR 全体をもう一度 `make review` する：直したことで入った欠陥も拾える。ただ、回数の上限が要り、「1回だけ」の決まりもゆるむ。
- 詰めたことは Issue の本文にだけ書き、ADR や CONTEXT.md は実装の途中で書く：ADR の文面を、決めた場（ユーザーとの対話）から離れたセッションが書くことになる。

## Consequences

- レビュー本文の「差分の外の指摘」はスレッドにならないので、address-review-comment では扱えない。implement-issue はそれをユーザーに見せ、1件ずつ直すかどうかを聞く。直したものは PR へのコメントで知らせる。
- `scripts/comment.sh`（`make comment`・`make reply`・`make unresolved`）は、自動実行で `gh api` を許さないために作った。いまは、決まった動きのコマンドにまとめ、スキルの手順を短くするために残している。
